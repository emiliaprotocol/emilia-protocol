# Go conformance: EP hybrid post-quantum verification

Runs the checked-in EP post-quantum vectors against the Go verifier
(`packages/go-verify`) with a **live FIPS 204 ML-DSA-65 backend**.

```
cd conformance/go && go test ./...
```

## What runs here

| vector file | profile | what this module adds |
| --- | --- | --- |
| `../pq-agility/vectors.json` | EP-SIG-AGILITY-v1 | the ML-DSA-65 legs actually verify |
| `../hybrid-receipts/vectors.json` | EP-RECEIPT-HYBRID-v1 | the ML-DSA-65 leg actually verifies, so `signature_invalid` is attributed to the right leg |
| `../vectors/pq-hybrid-envelope.v1.json` | EP-HYBRID-v1 | the PQ leg of the envelope actually verifies |

Every one of those vectors ALSO runs in
`packages/go-verify/pq_verification_test.go` with **no** backend, where the PQ
leg must refuse with `pq_backend_unavailable`. Together the two halves cover
each vector twice: once with the post-quantum leg live, and once proving that
an absent backend is a named refusal rather than a skipped check.

## Why this is a separate Go module

`packages/go-verify` states "Zero-dependency ... Standard library only" in its
README, ships without a `go.sum`, and its release workflow diffs the
checked-out tree against the bytes the Go module proxy serves. Go's standard
library has no exported ML-DSA-65 (only the unexported
`crypto/internal/fips140/mldsa`), so a live post-quantum leg requires a
third-party implementation.

Rather than spend the published verifier's dependency posture on it,
`packages/go-verify` takes the ML-DSA backend as an interface
(`emiliaverify.MldsaBackend`) and this module supplies one from
`github.com/cloudflare/circl/sign/mldsa/mldsa65`. Every STRUCTURAL control --
the closed algorithm registry, algorithm/key tagging, the exact signature and
public-key length pins, the Ed25519 curve pin, the algorithm-set commitment,
and the set policy -- is implemented in `packages/go-verify` and runs to
completion with or without a backend.

## Claim boundary

Read this before describing any of it outside the repository.

- The checked-in signature bytes were generated by `@noble/post-quantum`
  (pure JavaScript). That CIRCL (Go) accepts those exact bytes and rejects the
  tampered ones is **cross-implementation agreement on the FIPS 204 encoding**.
  It is not a certification claim: neither implementation is FIPS validated,
  and neither has completed an independent audit.
- A Go port of an `@emilia-protocol` profile, in this repository, is a
  **second implementation of our own specification**, not an independent
  implementation by an external party.
- VERIFIED here means the cryptographic checks pass. It never means ACCEPTED:
  nothing in this suite pins a trust root or evaluates issuer authority.
- This module is not registered in `conformance/suites.mjs` and does not change
  the published suite or vector totals, exactly as `conformance/pq-agility` and
  `conformance/hybrid-receipts` do not.
- Not wired into CI. `.github/workflows/go-verify.yml` runs `go test ./...`
  inside `packages/go-verify`, which does not cross a module boundary, so the
  backend-absent half runs in CI today and this live-backend half is run
  locally.
