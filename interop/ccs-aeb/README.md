# CCS to AEB experimental composition

This directory contains a runnable, source-locked composition between the
artifact actually emitted by the `ccs-verifier` PyPI distribution and the
EMILIA Action Evidence Boundary (AEB).

The composition keeps four claims separate:

1. CCS evaluates one tool invocation and emits a native policy result.
2. The AEB adapter verifies that native result under relying-party-owned pins.
3. CAID maps the verified CCS command to the exact action independently
   constructed by the executor.
4. AEB evaluates the complete evidence requirement and reserves every native
   replay identity before provider entry.

A CCS `allow` fills only the `machine-policy-decision` role. It does not become
human authorization, execution authority, provider entry, or effect evidence.

## Source lock and current implementation boundary

This profile targets the PyPI artifact labeled `ccs-verifier==1.1.0` as it was
available on 2026-08-10. The installed package reports `__version__ == "0.4.1"`
and its runtime result uses the older HMAC receipt shape.

The source distribution also contains `tests/test_l1_receipt_v11.py`, but the
`ccs_verifier_l1` module imported by that test is absent from both the wheel and
source archive. The advertised L1 test therefore fails during collection with
`ModuleNotFoundError`. The current package does not provide the extended
Ed25519 receipt described by the CCS drafts, so this adapter makes no such
claim.

Run the source audit in a disposable virtual environment:

```sh
python3 -m venv /tmp/ccs-aeb-audit
/tmp/ccs-aeb-audit/bin/pip install ccs-verifier==1.1.0
/tmp/ccs-aeb-audit/bin/python interop/ccs-aeb/audit_installed_ccs.py
```

The audit is read-only. It prints the distribution version, runtime version,
runtime result fields, and whether the L1 module is importable.

The checked-in positive fixture is generated by the installed package's own
`Command.params_hash()` and `sign_receipt()` functions, not by the adapter:

```sh
/tmp/ccs-aeb-audit/bin/python interop/ccs-aeb/generate_fixture.py
```

Its locked `params_hash` and receipt bytes are asserted by the Node suite.

## Security scope

The shipped CCS result uses a shared HMAC key. This profile therefore requires
one HMAC key scoped to one relying party and one audience. It is not a portable
third-party receipt.

The shipped `params_hash` covers only 64 bits. The adapter requires an explicit
`params_hash_bits: 64` pin and supports only an interoperable JSON subset with
ASCII strings and safe integer numbers. Deployments should not treat this
experimental profile as a high-assurance cross-domain action binding. A future
adapter revision can target a shipped full-digest, public-key CCS receipt
without changing AEB.

Fields that the shipped HMAC does not cover, including `agent_id`, command
timestamp, block reason, rule latency, and error code, are never material input
to the CAID mapping. Unknown fields are rejected. In particular, a presenter
cannot add `outcome_status: confirmed` and turn a pre-action policy result into
effect evidence.

## Run the mapping and hostile cases

Build the verifier package, then run the focused suite:

```sh
npm --prefix packages/verify run build
npm run build:standalone-runtimes
node --test packages/verify/aeb-ccs-adapter.test.js
```

The suite covers:

- a current CCS `allow` mapped to the exact executor action;
- approve-A / execute-B substitution;
- command-parameter mutation;
- receipt, tool, rule-set, and relying-party-pin substitution;
- native `deny` and `escalate`;
- stale and unavailable evidence;
- attempted promotion of a CCS outcome label into effect evidence; and
- a fresh CCS receipt attempting to reuse the same execution authority after
  an indeterminate provider attempt.

The final case is the load-bearing composition. A new CCS nonce proves only
that a new CCS decision was produced. It cannot refresh or clone the separate
execution authority. AEB reserves both native replay identities atomically, so
the second provider admission is refused.

## What independent reproduction would establish

An independent CCS run against this profile would establish only that the
current native CCS result can be verified, mapped, and composed under the
stated local-HMAC assumptions. It would not establish IETF adoption, CCS
conformance beyond the pinned source revision, EMILIA certification, complete
mediation, or successful provider effect.

The next positive interoperability target is a corrected CCS package that
actually exports its public-key L1 receipt implementation. That revision needs
one unambiguous signed-byte definition, full material-action digest coverage,
issuer and audience binding, freshness, and a replay identity. AEB can then
consume the native result without changing CCS's semantics.
