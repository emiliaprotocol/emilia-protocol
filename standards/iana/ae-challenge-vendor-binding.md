# EMILIA bare AE Challenge media-type serialization specification, Version 1

Status: Version 1 vendor product specification.

Media type:

    application/vnd.emilia.authorization-evidence-challenge+json

This document completely defines the bare UTF-8 JSON serialization of an
`AE-CHALLENGE-v1` object for this vendor media type. It does not define a
complete carrier or presentation protocol, request IETF adoption, or depend on
the publication of an Internet-Draft.

The key words **MUST**, **MUST NOT**, **REQUIRED**, **SHALL**, **SHALL NOT**,
**SHOULD**, **SHOULD NOT**, **RECOMMENDED**, **NOT RECOMMENDED**, **MAY**, and
**OPTIONAL** in this document are to be interpreted as described in BCP 14
[RFC 2119] [RFC 8174] when, and only when, they appear in all capitals.

## Representation

The representation is one UTF-8 JSON text whose top-level value is one object.
It is not a JSON text sequence and does not use record-separator framing. A
recipient **MUST** reject duplicate member names at every object depth before
authenticating, hashing, registering, or evaluating the object.

A generic `+json` processor can parse the representation but does not thereby
implement challenge semantics. This specification does not select a JSON
canonicalization profile.

The following example is non-normative:

```json
{
  "@version": "AE-CHALLENGE-v1",
  "challenge_id": "7a3120d1-65b4-4d1a-85d4-9128adf76b41",
  "nonce": "ABEiM0RVZneImaq7zN3u_w",
  "action_digest": "sha256:aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
  "action_profile": "https://example.net/action/payment-v3",
  "audience": "https://gateway-a.example",
  "policy_id": "https://gateway-b.example/policies/high-risk-v4",
  "policy_digest": "sha256:bbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb",
  "required_evidence": [
    {
      "requirement_id": "human-approval",
      "type": "https://example.net/e/authorization-receipt",
      "profiles": ["https://example.net/profiles/receipt-v1"],
      "max_age_sec": 300,
      "status": "current"
    }
  ],
  "present_as": ["https://example.net/p/ep-aec-v1"],
  "obtain_hints": [
    {
      "requirement_id": "human-approval",
      "mechanism": "https://example.net/flows/approval-v1",
      "uri": "https://approver.example/tasks/123"
    }
  ],
  "retry_timing": {
    "not_before": "2026-08-09T23:50:30Z",
    "jitter_sec": 20
  },
  "expires_at": "2026-08-10T00:05:00Z"
}
```

## Core members

An object **MUST** contain `@version`, `challenge_id`, `nonce`,
`action_digest`, `action_profile`, `audience`, `policy_id`, `policy_digest`,
`required_evidence`, `present_as`, and `expires_at`. The `obtain_hints`,
`retry_timing`, and `critical` members are optional. A member defined as an
array **MUST** be a JSON array; a recipient **MUST NOT** promote a scalar into
an array.

- `@version` **MUST** be the string `AE-CHALLENGE-v1`. A recipient that does
  not implement this version **MUST** refuse automated processing.
- `challenge_id` **MUST** be a non-empty JSON string. It is an opaque
  correlation identifier and is not a replay key. Authorization decisions
  **MUST NOT** depend on its global uniqueness.
- `nonce` **MUST** encode at least 16 random octets generated by a
  cryptographically secure source consistent with RFC 4086 as unpadded
  base64url under RFC 4648 Section 5. It **MUST** contain 22 through 128 ASCII
  characters and is compared as an exact, case-sensitive string.
- `action_digest` and `policy_digest` **MUST** use the case-sensitive string
  `sha256:` followed by 64 lowercase hexadecimal digits, using SHA-256 as
  defined by RFC 6234. `action_digest` identifies the action bytes defined by
  `action_profile`. The security action binding is the ordered pair
  (`action_profile`, `action_digest`), not the digest alone. `policy_digest`
  hashes a deterministic relying-party representation of local policy. It
  identifies the policy state that produced the challenge and does not
  transfer that policy to the recipient.
- `action_profile` and `policy_id` **MUST** be absolute-URI strings.
  `action_profile` identifies the deterministic mapping or canonicalization
  used to produce `action_digest`.
- `audience` **MUST** be a non-empty JSON string. The carrier or presentation
  profile defines its identifier namespace and exact comparison rule.
- `required_evidence` **MUST** be a non-empty array of evidence-requirement
  objects defined below.
- `present_as` **MUST** be a non-empty array of unique absolute-URI strings.
  Each value identifies an alternative presentation profile; their order
  expresses preference, not a security ranking.
- `expires_at` **MUST** be an Internet timestamp under RFC 3339. A relying
  party **MUST** refuse an expired challenge before evidence or policy
  evaluation.

The relying party **MUST** compute `action_digest` from the exact action it
would admit under its pinned `action_profile`; it **MUST NOT** copy either
value from a presenter. At evaluation time it uses authenticated live policy,
not policy supplied by the presenter.

## Evidence-requirement objects

Every object in `required_evidence` **MUST** contain:

- `requirement_id`: a non-empty string unique within the challenge; and
- `type`: an absolute-URI string identifying the evidence type.

An evidence-requirement object may also contain:

- `profiles`: a non-empty array of unique absolute-URI strings. The listed
  profiles are alternatives for this requirement.
- `proof_predicates`: a non-empty array of unique absolute-URI strings. Every
  listed predicate is conjunctive.
- `max_age_sec`: an integer from 0 through 2147483647 inclusive.
- `status`: a non-empty string. This specification defines `current`; a
  recipient **MUST** refuse another value unless an applicable profile defines
  it.

`max_age_sec` is measured at the relying party's evaluation time using the
issuance or observation time defined by the selected evidence profile.
`current` requires a separately authenticated status result satisfying the
relying party's freshness policy; absence from an unauthenticated revocation
list is not sufficient. The relying party or its authoritative owner selects
the evaluation-time source; presenter- or caller-supplied time **MUST NOT**
make stale evidence appear fresh.

Every element of `required_evidence` is conjunctive. A relying party
**MUST NOT** treat the challenge as satisfied unless every requirement is satisfied.
Unless the specification for an identifier states otherwise, URI identifiers
are compared as exact strings. A recipient **MUST NOT** infer security
semantics from a URI prefix or substring.

Evidence-requirement objects are closed. A recipient **MUST** reject an
unknown member in one of these objects unless the enclosing presentation
profile explicitly defines it.

## Acquisition hints

If present, `obtain_hints` **MUST** be an array of closed JSON objects. Each
object **MUST** contain `requirement_id`, `mechanism`, and `uri` string members.
`requirement_id` **MUST** identify a requirement in the same challenge;
`mechanism` and `uri` **MUST** be absolute URIs.

Multiple hints for one requirement are unordered alternatives unless an
application profile defines ordering.

Hints are untrusted routing inputs. Following a hint or receiving an approval
from its target grants no authority. A recipient **MUST NOT** send credentials
or evidence to a hinted endpoint unless its own policy independently permits
the endpoint, scheme, redirect behavior, and disclosed material.

## Retry timing

If present, `retry_timing` **MUST** be a closed JSON object containing a
`not_before` RFC 3339 Internet timestamp and, optionally, `jitter_sec` as an
integer from 0 through 2147483647 inclusive. `not_before` **MUST** precede
`expires_at`; adding `jitter_sec` to `not_before` **MUST** still produce an
instant before `expires_at`.

`not_before` is only the earliest time to present corrected evidence. It is
not evidence satisfaction, authorization, or a promise of capacity or
execution. `retry_timing` is safe to ignore for challenge semantics and
**MUST NOT** appear in `critical`.

## Extensions

If present, `critical` **MUST** be an array of unique, non-empty strings. Each
string **MUST** name an unknown top-level member that is present in the same
object. It **MUST NOT** name a core member. A recipient **MUST** ignore an
unknown top-level member unless its name appears in `critical`; if it appears
there and the recipient does not understand it, the recipient **MUST** refuse
automated processing.

The closed nested objects in `required_evidence`, `obtain_hints`, and
`retry_timing` do not use this extension rule.

## Validation and resource limits

Arrays that this specification requires to be unique **MUST** be checked after
duplicate-member rejection. A recipient **MUST** refuse a requirement whose
`status` or `proof_predicates` semantics it does not understand; it
**MUST NOT** treat an unknown value as satisfied.

Implementations **MUST** apply finite limits to encoded message size, nesting
depth, numbers of requirements and hints, array lengths, string lengths, and
retained state before expensive cryptographic, evidence, network-status, or
policy work.

## Carrier boundary

This media type labels only the bare object. It does not authenticate the
issuer or recipient, bind an effective audience, define a response or
presentation carrier, or provide replay protection.

Every carrier or presentation profile that uses this media type **MUST**
define:

- how every core and extension member is preserved;
- authenticated issuer identity and presenter-to-audience binding;
- the audience identifier namespace, alias handling, and comparison rule;
- a domain-separated complete-body digest with at least 256 bits of output,
  covering every core and extension member after duplicate-member rejection,
  with deterministic representation or exact-byte preservation;
- the authoritative replay domain and atomic first-claim procedure keyed by
  authenticated issuer identity and `nonce`;
- a trustworthy evaluation-time source and expiry procedure;
- exact-action rederivation and authenticated comparison of both
  `action_profile` and `action_digest`; and
- how a presentation identifies its profile, returns the challenge or an
  authenticated immutable reference, maps evidence to `requirement_id`, and
  reports refusal or other return-path semantics.

This media type **MUST NOT** label an HTTP Problem Details envelope. A carrier
that embeds the object in such an envelope uses the envelope's media type,
such as `application/problem+json`, and separately defines the embedding
member and its semantics.

## Security considerations

An AE challenge authorizes nothing. Satisfying one does not reserve an action,
consume action authority, promise execution, or establish that an external
effect occurred.

The representation contains declarative JSON and no active or executable
content. It uses neither compression nor a container format. It provides no
origin authentication, integrity, confidentiality, replay protection, trusted
time, or audience verification. Those properties belong to a carrier or an
authenticated envelope.

URI-valued semantic identifiers **MUST** be locally pinned or resolved only
from immutable, authenticated content. Mutable interpretation of
`action_profile`, evidence types or profiles, presentation profiles, or
audience aliases can silently weaken validation. Dereferencing a URI is not
required to parse this media type.

Single-use handling requires an authoritative replay domain keyed by
authenticated issuer identity and `nonce`, plus an atomic first-claim
transition. Expiry and nonce randomness do not replace that state. A live
replay key **MUST NOT** be overwritten. Uncertain replay-store or claim state
fails closed.

Action and policy digests do not hide low-entropy values and do not prove
business correctness or execution. Confidentiality appropriate to the
deployment is required when a challenge exposes sensitive action, policy,
identity, evidence, or routing information. Implementations also apply the
JSON security considerations in RFC 8259 Section 12.
